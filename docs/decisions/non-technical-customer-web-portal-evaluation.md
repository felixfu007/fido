## 0. 商業模式前提（第一原理）

`README.md` 與 `docs/vendor/*.md` 五份手冊的定位很清楚：這是**一套要授權/賣給其他電商廠商整合的 FIDO2 平台**。擁有者本次點出一個先前評估都沒正面處理的前提：

> **買這套系統的客戶（採用廠商），不是技術人員。**

而現況五份手冊的**預設讀者全是「客戶的工程/維運團隊」**，逐份查證：

- `api-integration-guide.md` 開宗明義「**適用對象：採用廠商的後端工程師**」——教 server-to-server 呼叫、JWT 驗簽、IDOR 責任邊界、`assetlinks.json`、`amr` step-up。
- `environment-setup-guide.md`「**適用對象：採用廠商的維運 / 基礎設施團隊**」——教在**自有環境部署 `fido-server` 與其專屬 SQL Server**、跑六支 DDL、TDE、備份 Job。
- `maintenance-guide.md`「**適用對象：採用廠商的維運 / SRE 團隊**」——備份還原、TDE 憑證保管、監控告警、升級。
- `technical-limitations.md`「適用對象：技術決策者與售前」。
- `usage-scenarios-guide.md` 是唯一標「**較不技術**」的一份（產品/客服/導入團隊）。

**落差一目了然：五份手冊裡有四份預設客戶端有工程或維運團隊。若客戶端根本沒有這樣的人，這個落差必須正面分析，不能迴避。** 這正是本文的主軸。

## 1. 釐清「客戶」在現有架構裡實際要做什麼、由誰做（最關鍵的一層區分）

擁有者要求：不要只回答表面的「加個網站就好」，要先點出**問題的真正層次**。把「一個租戶從簽約到終端使用者能用 FIDO」拆成四層，逐層標「由誰做」：

| 層 | 內容 | 現況由誰做 | Web 後台 / Portal 能不能代勞？ |
|---|---|---|---|
| **L0 開通** | `create-tenant` / `add-app-binding` / `rotate-signing-key`（產 API Key、登錄 App 簽章、輪替金鑰） | **賣方（我們）**在 fido-server 主機跑 admin CLI；客戶不碰，只收 API Key + 文件 | **能**（若做內部後台或自助 Portal） |
| **L1 整合（大魔王）** | 在**客戶自己的購物網站後端**寫 server-to-server 呼叫、JWKS 驗 JWT、`externalUserId` IDOR 把關；原生 App 情境還要處理 Credential Manager + `assetlinks.json`；情境三要做 `amr` 含 `xdev` 的 step-up 授權 | **客戶自己的工程團隊** | **不能**——這是客戶自家程式碼，fido-server 有沒有 UI 與此無關 |
| **L2 部署與運維** | 在**客戶自有環境**部署 fido-server + SQL Server、跑六支 DDL、TDE 憑證保管、備份/還原、清理 Job、升級（`environment-setup-guide.md` §1 明載「由採用廠商部署」） | **客戶自己的維運/SRE** | **不能**——這是客戶自有主機/DB 的事，portal 管不到 |
| **L3 營運/客服** | 看自己租戶的裝置清單/稽核/用量、協助撤銷 | 部分已有：客戶購物網站可用代理端點（`/shop/api/fido/devices` list/revoke）、稽核查詢端點 §5.2 給終端使用者/自家後台；平台層彙總目前只能查 DB | **部分能**（見 §2） |

**這張表就是擁有者要我點出的層次區分**：

> **「客戶不是技術人員」真正卡住的是 L1 與 L2，而 Web 後台/Portal 頂多只能碰 L0 和 L3。** 一個管理後台就算做到完美，**也完全解決不了 L1（客戶購物網站的串接程式碼）與 L2（客戶自有環境的部署與運維）**——因為那些是**客戶自己系統裡要寫的程式碼、要顧的主機**，跟 fido-server 有沒有 Web UI 無關。除非商業模式改成「我們連客戶的購物網站整合與部署都代管/代寫」（見 §4 選項 c），否則沒有任何 fido-server 端的 UI 能填 L1/L2。

### 1.1 一個必須先釐清的歧義：「非技術」是哪一種？

「客戶不是技術人員」有兩種截然不同的意思，答案完全不同：

- **語意甲（組織層級無工程能力）**：客戶是小型電商，**整個公司沒有工程團隊**。→ 那麼連「拿 API + 文件自己串」這個現有模式本身就不成立，L1/L2 直接卡死，portal 幫不上忙，唯一出路是 §4 選項 c（代管/代寫）。
- **語意乙（決策者/操作者/客服非技術，但公司有工程團隊）**：拍板的人、日常操作/客服的人不懂技術，但公司**有工程團隊**能做 L1/L2 整合。→ 那麼缺口只在 L0（開通）與 L3（營運/客服視圖），此時 §4 選項 a/b 才有討論意義。

**這個歧義是決定性的，只有擁有者能回答，且它決定了後面所有選項的取捨。** 本文兩種都涵蓋，但請擁有者先明確是哪一種。

### 1.2 附帶查到的一個既有張力（非本次新問題，但在「非技術」前提下會被放大）

兩處既有文件對「誰擁有 fido-server 主機」的描述其實存在張力，在客戶非技術時會變得尖銳：

- `environment-setup-guide.md` §1：fido-server 與 SQL Server **由採用廠商自行部署**（客戶擁有主機）。
- `CLAUDE.md` 與 `environment-setup-guide.md` §6：`create-tenant` 等 CLI **由平台維運方（賣方）在伺服器主機上執行**。

兩者並存，隱含的模型是「**客戶擁有主機、但賣方要能登入該主機跑 CLI**」。這在客戶有維運團隊時或許能靠遠端協作 workaround；但**若客戶非技術、又是全地端自有主機，「賣方遠端進客戶主機開通」本身已經是一種專業服務/代管性質的介入，不是純產品銷售**。這反而是 §4 選項 c 的伏筆——「非技術客戶 + 自有部署 + 賣方代跑 CLI」在實務上幾乎必然滑向代管。此點列為觀察，不在本文拍板。

## 2. Web 後台/Portal 能解決的，與解決不了的（分開列）

### 2.1 能幫上忙的（僅限 L0、L3）

1. **客服/營運看自己租戶的裝置清單、稽核、用量，不必學 SQL**：目前平台層彙總只能直接查 DB。一個（給我們客服用、或給客戶自助用的）唯讀畫面能取代「求助工程下 SQL」。
   - *但要注意*：客戶購物網站**對終端使用者**的裝置管理，`shopping-site-reference` 的 `DeviceProxyController` 代理端點已經示範可做（L3 的一部分其實已被覆蓋）；真正缺的是「租戶層級彙總視圖」給客戶的營運/客服，而非給終端使用者。
2. **客服人員用後台替非技術客戶做開通，取代「SSH 進主機跑 CLI」**：把 L0 從命令列變成點按。**但這解決的是「賣方客服的操作便利性」，因為 L0 本來就是我們的事**（見 §1 表）——本質仍是內部工具，與前一份 admin-backend 評估的方案 B/C 是同一個問題。
3. **（只有商業模式改成自助時才成立）客戶自助**：客戶自己看用量、下載整合文件、甚至自助開通試用租戶。這**不是** L0 便利化，而是**把 L0 的操作者從賣方改成客戶**——是一個全新的、對外、帶認證、多租戶隔離（只能看/改自己租戶）的**客戶自助 Portal**，與現行 CLI 決策解決的「單機平台維運」是兩件事（§3 詳述）。

### 2.2 解決不了的（L1、L2，無論做不做 UI）

以下全部是**客戶自有系統/主機裡的事**，fido-server 端任何 UI 都碰不到，除非商業模式變成代管/代寫（§4 c）：

- 客戶購物網站後端的 **server-to-server 串接程式碼**（呼叫 options/result、代理裝置管理）。
- **session JWT 驗簽邏輯**（JWKS 取公鑰、驗 ES256、檢 iss/aud/exp、jti 一次性）。
- **`externalUserId` IDOR 把關**（`api-integration-guide.md` §6 的責任邊界，寫在客戶後端）。
- **原生 App 的 Credential Manager 呼叫 + `assetlinks.json` 部署**。
- **情境三 `amr` 含 `xdev` 時對敏感操作要求 step-up**的授權邏輯（`api-integration-guide.md` §11.3，enforcement 落在客戶後端）。
- **L2 全部**：部署 fido-server/SQL Server、六支 DDL、TDE 憑證保管、備份還原、升級。

**一句話總結 §2：Web 後台能把「開通」和「營運查詢」變得對非技術者友善（L0/L3），但它從結構上碰不到讓非技術客戶真正卡住的整合與運維（L1/L2）。把「要不要做後台」當成非技術客戶問題的答案，會答錯層。**

## 3. 重新檢視「CLI-only、不開對外管理端點」在「客戶非技術」前提下是否站得住腳

既有決策（`CLAUDE.md`）的三支柱：(a) 全地端、操作者是平台維運方本人；(b) 能 shell 進主機＝隱含強認證、零新增攻擊面；(c) 開對外端點要另立一組平台管理金鑰，形成雞生蛋問題、對唯一合法呼叫者無便利淨益。

**關鍵觀察：這條決策從頭到尾預設「開通這件事本來就是我們自己做，不是客戶做」（L0 由賣方執行）。因此它與「客戶是否技術」在字面上是正交的——客戶技不技術，都不改變「開通由賣方跑」這個前提。** 只要 L0 仍由賣方做，CLI-only 就仍站得住腳，非技術客戶前提對它毫無衝擊。

**唯一會動搖它的，是擁有者的真正意圖若為「讓客戶自己（哪怕非技術）也能自助完成部分操作」**：

- 若只是「客戶自助**唯讀**看用量/裝置/稽核」→ 這需要一個**對外、帶認證、多租戶隔離的客戶自助 Portal**。這**不是** CLI 決策要解的問題（那是單機平台維運），是**新增能力**，兩者不衝突也不互斥——CLI 繼續管特權寫入，Portal 只做客戶唯讀自助。但要誠實標註：Portal **觸及 `audit_log` 個資**（含 `user_ref_id`/`ip_address`/`detail`），且是**對外、多租戶**，PII 攻擊面比前一份評估的「內網唯讀 UI」更高，需嚴格租戶隔離（只能看自己租戶）、強認證、對查詢本身留稽核、限制匯出。
- 若意圖是「客戶自助**開通/寫入**（自己 create-tenant、輪金鑰、綁 App）」→ **這直接與「CLI-only、不開對外管理端點」決策衝突**。當初否決對外管理端點的理由（雞生蛋的平台管理金鑰、擴大攻擊面）在「對外、多租戶、非技術操作者」情境下**全數重新成立且更嚴重**。**此處明確標示為衝突**：若要走這條，等於重新開啟並修改該拍板決策，需正式重議、由擁有者拍板。

**小結 §3：CLI-only 決策在「L0 仍由賣方做」的前提下不受非技術客戶前提影響、仍站得住腳。它只有在擁有者想把 L0 交給客戶自助時才需要重議——而那本質上是「新增一個客戶自助 Portal」這件新事，不是推翻 CLI，兩者不要混為一談。**

## 4. 選項與建議

先強調一個貫穿所有選項的事實（§1、§2 的結論）：**沒有任何選項能靠 fido-server 端的 UI 解決 L1/L2；能解 L1/L2 的只有選項 c（商業模式調整）。** 因此選項 a/b 只在「語意乙（客戶有工程團隊）」下是完整答案；在「語意甲（客戶無工程團隊）」下，a/b 都不足以讓客戶真的用起來。

### 選項 a：維持現狀 + 非技術客戶依賴我們的技術支援 / 客服人工代操作

L0 開通由賣方客服用**既有 CLI**（或加一個**內部後台**，即前一份 admin-backend 評估的方案 B/C 範疇）代辦；L3 營運/客服查詢用唯讀 DB 帳號 + SQL/BI，或加 `list-tenants` 等唯讀 CLI 指令；L1/L2 仍要求客戶端有工程/維運團隊自行完成。

- **對「非技術客戶」前提的解決程度**：**只在語意乙成立**（客戶有工程團隊、只是決策者/客服非技術）。**在語意甲下不成立**——L1/L2 無人能做，客戶根本上不了線。
- **實作成本量級**：**小**（沿用既有 CLI；內部後台若做，成本同前一份評估方案 B 的中）。
- **與九張表 / 多租戶架構相容性**：**完全相容**（不新增對外面、不動 schema）。
- **與 CLI-only 決策**：**完全相容**（是它的自然延續）。

### 選項 b：客戶自助 Portal（唯讀為主）

對外、帶登入、多租戶隔離的客戶自助畫面：客戶只能看**自己租戶**的裝置清單、稽核、用量；寫入（撤銷裝置）多半客戶購物網站本來就有代理端點，Portal 不必重造；開通/輪金鑰等特權寫入**仍留 CLI**（守住既有決策核心）。

- **對「非技術客戶」前提的解決程度**：**部分（僅 L3）**。讓非技術客戶不必求助工程即可自己看狀態；但 **L1/L2 仍卡死**，語意甲下客戶依舊上不了線。
- **實作成本量級**：**中～大**。前後端 + 對外認證 + **嚴格租戶隔離**（越權查別租戶＝重大事故）+ 觸及 `audit_log` 個資的存取控制 + 對查詢本身留稽核 + 限制匯出。比前一份評估的「內網唯讀 UI」風險更高（此為**對外、多租戶**）。
- **與九張表 / 多租戶架構相容性**：**相容**（多租戶隔離本就是 `X-API-Key`→tenant 的既有模型；Portal 的租戶隔離可沿用同一把關）。可能需為 Portal 登入身分新增一張使用者/憑證表（非九張核心表範圍），或接既有 SSO。
- **與 CLI-only 決策**：**部分相容**（守住特權寫入走 CLL；但引入了「對外、需登入」的東西，與「不開對外管理端點」精神有張力，需擁有者對個資/攻擊面權衡簽核）。若 Portal 進一步納入**自助開通/寫入**，則升級為**與 CLI-only 決策衝突**（見 §3）。

### 選項 c：更大幅度的商業模式調整（代管 / 半代管整合服務）

平台方不再「只給 API + 文件」，而是提供**代管或半代管**：例如 (i) 我們代客戶部署並運維 fido-server + SQL Server（解 L2）、(ii) 提供 turnkey 的購物網站整合套件/外掛或由我們的專業服務代寫串接（解 L1）、(iii) 甚至改為我方託管的多租戶 SaaS。

- **對「非技術客戶」前提的解決程度**：**唯一能真正解語意甲的選項**——因為它直接接手 L1/L2。這才是「客戶完全沒有技術人員也能用」的實際答案。
- **實作成本量級**：**最大，且不只是工程**——是產品定位、交付模式、營運人力（專業服務團隊）、責任/SLA、計價模式的全面改變。
- **與九張表 / 多租戶架構相容性**：核心九張表與多租戶模型**本身相容**（多租戶隔離已在）；但 SaaS 託管會**直接牴觸 `CLAUDE.md`「部署：全地端部署（非雲端）」**，代管客戶主機也可能牴觸「非身分來源 / 個資最小化」定位（我們會持有更多客戶側運維接觸面）。
- **與 CLI-only 決策**：CLI 本身可續用（改由我方代管團隊在託管主機上跑）；**但與「全地端部署（非雲端）」等多條決策衝突**，屬**商業模式層級的重議**，需擁有者正式拍板、非 systems-analyst 可定。**明確標示為衝突（商業模式層級）。**

### 選項比較總表

| 選項 | 解決層次 | 對「非技術客戶」前提 | 實作成本 | 與多租戶/九張表相容 | 與既有決策 |
|---|---|---|---|---|---|
| **a 現狀+客服代操作** | L0（賣方）、L3（SQL/BI/CLI） | 僅語意乙成立；語意甲不成立 | 小 | 完全相容 | 與 CLI-only 完全相容 |
| **b 客戶自助 Portal（唯讀）** | 加 L3 自助 | 部分（僅 L3）；L1/L2 仍卡 | 中～大 | 相容（隔離沿用；登入身分或需新表） | 唯讀＝部分相容需簽核；含自助寫入＝**衝突** |
| **c 代管/半代管** | L1 + L2 + L0/L3 | **唯一能解語意甲** | 最大（含營運/商模） | 核心相容；SaaS 牴觸「全地端」 | **商業模式層級衝突**，需重議 |

## 5. 專業建議（建議，非決策，由擁有者拍板）

**第 0 步、也是最重要的一步：請擁有者先回答 §1.1 的歧義——「非技術」是語意甲（無工程團隊）還是語意乙（有工程團隊、只是操作者非技術）。** 這一題不定，後面全是空談，因為它決定「portal 夠不夠」還是「非改商業模式不可」。

在此前提下，傾向建議：

1. **不要把「加 Web 後台」當成非技術客戶問題的答案——那會答錯層。** 真正的瓶頸是 L1（客戶購物網站串接程式碼）與 L2（客戶自有部署運維），這兩層是客戶自家系統的事，**任何 fido-server 端 UI 都填不了**。這是本評估最需要被擁有者聽進去的一句。

2. **若是語意乙（客戶有工程團隊）→ 傾向選項 a，先不做客戶自助 Portal。**
   - L0 開通維持賣方用 CLI（或依前一份 admin-backend 評估決定要不要加**內部**客服後台）。
   - L3 客戶營運/客服查詢：客戶對**終端使用者**的裝置管理已可用 `shopping-site-reference` 示範的代理端點自建；租戶層彙總先用唯讀 DB/BI 或 `list-tenants` 類唯讀 CLI 承接。
   - 對外、多租戶、觸及 `audit_log` 個資的客戶自助 Portal（選項 b），**邊際價值低、PII/攻擊面成本高**，建議列為「觀察後再議」的觸發式選項：只有當「非技術客戶頻繁要求自助查詢、且無工程可代勞」成為反覆出現的實際營運痛點時再升級，且升級前需擁有者對個資法/攻擊面/租戶隔離權衡簽核。

3. **若是語意甲（客戶無工程團隊）→ 誠實說：portal 救不了，要面對的是選項 c（商業模式）。** 沒有工程團隊的客戶，L1/L2 無人能做，給再漂亮的自助 Portal 也上不了線。此時真正該決策的不是「做不做後台」，而是「**我們要不要從賣 API+文件，轉成賣代管/半代管的整合服務**」——這是產品定位、交付模式、營運人力、計價、以及是否鬆動「全地端部署（非雲端）」等多條既有決策的重大取捨，**明確標示為商業模式層級衝突，須擁有者正式重議，systems-analyst 不越權替您拍板。**

4. **明確標示的衝突（不默默覆蓋）：**
   - **客戶自助「開通/寫入」Portal** → 與「CLI-only、不開對外管理端點」拍板決策**衝突**（§3）。
   - **代管/SaaS 託管** → 與「全地端部署（非雲端）」等決策**衝突**（§4 c），屬商業模式重議。
   - **客戶自助「唯讀」Portal** → 與「不開對外管理端點」精神**部分張力**，且新開一條觸及 `audit_log` 個資的對外多租戶路徑，需簽核。

**這只是傾向。** 最終取捨取決於兩個只有擁有者能回答的問題：(1) §1.1 的「非技術」到底是哪一種；(2) 願不願意為了服務非技術客戶，把商業模式從「產品銷售」往「服務/代管」移動。無論選哪個方向，建議動工前先把結論（含 Portal 若做的「租戶隔離 + `audit_log` 個資存取控制 + 對查詢留稽核」要求，或代管若做的「全地端決策是否鬆動」）寫進本文或 `CLAUDE.md`，再交 dev-engineer / devops-engineer 承接。本次 systems-analyst 僅出評估，不指示實作、不動程式碼、不動 `CLAUDE.md`。
