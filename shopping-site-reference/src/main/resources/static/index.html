購物網站 FIDO 串接參考範例（非正式產品）

這不是真正的購物網站，只是示範購物網站後端要怎麼呼叫 fido-server 的 REST API 完成 FIDO 加掛登入的串接（docs/api-contract.md）。畫面陽春、沒有商品/購物車/金流， 重點是能讓人手動點過一次完整流程、看得懂串接邏輯在哪裡。

重要（WebAuthn 瀏覽器限制）：本頁呼叫的種子租戶 rp_id = shop.example.com， 瀏覽器要求 navigator.credentials.create()/get() 的呼叫頁面 origin 的網域必須等於 （或是其可註冊子網域）這個 rp.id。也就是說，若不是真的把本頁部署在 https://shop.example.com（或其子網域）底下開啟，瀏覽器會直接拒絕整個 ceremony （SecurityError），與後端程式碼是否正確無關。本機測試需要先把 shop.example.com 導向本機（hosts 檔）並用受信任的本機憑證（例如 mkcert）以 HTTPS 開啟本頁，詳見專案交付說明。

0. 購物網站登入（示範用「假登入」）

對齊 CLAUDE.md：身分權威來源是購物網站既有帳密系統，FIDO 只是加掛選項；發起 FIDO 裝置註冊、 查看/撤銷裝置，前提都是「已經用帳密系統登入」。本頁沒有實作真正的帳密驗證 （不是本範例的重點）—— 下面按下「登入」時，只是呼叫一支示範用端點 POST /shop/api/session/login-as，帶入 externalUserId 就視為「已通過帳密驗證」， 直接核發購物網站自己的 SHOP_SESSION cookie。 正式串接時請把這一段整套換成你自己真正的帳密登入系統 （見 DemoLoginController 的 Javadoc）。

下面第 1、3 節（註冊 FIDO 裝置、裝置管理）都改成從這個登入 session 取得 externalUserId， 畫面上不會再出現讓你直接輸入 externalUserId 代表「目前已登入使用者」的欄位 —— 那正是本次 修正要杜絕的錯誤模式（IDOR）。

2. 用 FIDO 登入

    

      這是「用 FIDO 取代帳密登入」的流程，前提是尚未登入（或想改用另一個裝置登入）——
      這裡輸入 externalUserId 是在告訴 fido-server「我宣稱是誰」，實際身分驗證由 WebAuthn
      簽章完成，與上方第 0 節的登入 session 無關。留空則走 discoverable / usernameless 流程。
      登入成功後，購物網站後端會先驗證 fido-server 回傳的 session JWT（簽章 / iss / aud / exp /
      jti），驗證通過才會建立購物網站自己的 SHOP_SESSION cookie（等同於完成第 0 節的登入）。
